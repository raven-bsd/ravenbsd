# Pi 4 platd platform handles (P12, P8b)

Status: the `platd` capability plan, the P8b multi-window launcher and the fake launch qtest are
OBSERVED on the development host. The real hardware launch and the Pi 4 board are UNVERIFIED.
P8b makes the production entry expressible: devd creates the three MMIO windows in declaration
order, then the DMA buffer. No board result is claimed.

## 1. Resource table

`platd`'s hardware backend needs four distinct capabilities. The supervisor passes each as
`name=handle:length`; the parser rejects a missing/duplicated handle, a reserved slot (0/1/2) or
a window shorter than the register block.

| Resource | Pi 4 firmware window | Minimum length | Argument |
|---|---|---|---|
| VideoCore mailbox | `0xFE00_B880` + `0x40` | `0x40` | `mailbox=HANDLE:64` |
| BCM2711 GPIO | `0xFE20_0000` + `0xB4` | `0xB4` | `gpio=HANDLE:180` |
| RNG200 | `0xFE10_4000` + `0x28` | `0x28` | `rng=HANDLE:40` |
| Mailbox DMA buffer | supervisor DMA pool | `0x100` | `dma=HANDLE:256` |

The handles must be distinct and at least 3; a fresh P8 child has self (0), initfs (1) and
namespace (2). The hardware backend maps only these windows. A direct-DMA or clock resource is
not part of this ticket.

`platd`'s `--fake` backend is selected with `fake`/`fake=1` and does not map any capability; the
qtest uses it because QEMU `virt` has no BCM2711 mailbox/GPIO/RNG200.

## 2. P8b multi-window launch

`devd dtb launch` selects a platform node, creates every declared MMIO window in declaration
order, then the DMA buffer and optional IRQ, transfers the handles and waits for the driver.
Repeated `bar=N` selectors are the manifest form; the plan also accepts `mmio=N,N,...` when a
caller can carry the comma (the small `[[driver]]` table splits `args` on commas).

`platd` declares three MMIO windows (mailbox, GPIO, RNG200) plus one DMA buffer. The fixture table
uses:

```toml
args = ["bar=0", "bar=1", "bar=2", "resources=dma", "dma_size=256", "fake",
        "mailbox=3:64", "gpio=4:180", "rng=5:40", "dma=6:256"]
```

`devd` creates BAR slots 3/4/5 in declaration order and DMA slot 6. The named tokens are the
platd hardware plan's slot/length declarations; `fake` selects the deterministic backend in the
qtest. The generated `bar`/`bar_size` tokens describe the first window, and the handle order
identifies the rest. A duplicate `reg`, an out-of-range window, or a partial creation failure is
rejected/cleaned before the child can use a partial grant.

The single-BAR path used by genet/emmc2 is unchanged: `bar=0 resources=dma+irq` still produces
one BAR, then DMA, then IRQ with the existing token shape. The launcher tests cover both path
shapes.

The 3-window fixture DTB is
`tests/fixtures/pi4-platd/pi4-platd.dtb.hex` (generated by `generate.py`); the P8 `pi4-devd`
fixture remains the single-window Pi 4 tree.

## 3. Scheme transcript

The client starts after devd's readiness gate (`scheme:plat`) and exercises the existing `plat:`
scheme. The fixture runs devd under the `pcid` service name because init's root-device grant is
reserved for `pcid` (the same workaround as the P8 fixture); the production profile needs the
P10/REL3 grant policy.

```
devd: dtb devices=1
devd: dtb device /platd@fd580000 compatible=raven,pi4-platform reg=0xfd580000+0x1000 dma=0 irq=none
devd: dtb driver platd compatible=raven,pi4-platform device=/platd@fd580000
devd: dtb launch platd bars=3 bar=0 size=0x1000 dma=4096 irq=0
platd: ready backend=fake
svcd: pcid up
pi4-platd: model=0x00002711
pi4-platd: revision=0x00c03114
pi4-platd: serial=0x0000000012345678
pi4-platd: mac=02:00:00:00:00:01
pi4-platd: clock12=50000000
pi4-platd: power0=1
platd: claim pin=17
pi4-platd: gpio claim ok
platd: conflict pin=17
pi4-platd: gpio conflict ok
pi4-platd: gpio config ok
platd: release pin=17
pi4-platd: rng=ad4df30bae771bdc
pi4-platd: done
svcd: plat-client up
svcd: settled
init exited (0)
```

These are the deterministic fake values; they are not board register readings. The qtest case is
`tests/qtest/cases/pi4-platd.toml`, x86_64, with 23 matched expectations and no forbidden panic.

## 4. REL3 profile edit

P8b makes the production entry expressible. REL3 owns the profile and DTB edit: add a platd
platform node with three `reg` windows, the driver entry below, enable devd and keep the separate
platd service disabled. The compatible string must match the node.

`userland/servers/devd/drivers.toml` (one-line `args`; the small table parser splits on commas):

```toml
[[driver]]
name = "platd"
compatible = "raven,pi4-platform"
exec = "/sbin/platd"
args = ["bar=0", "bar=1", "bar=2", "resources=dma", "dma_size=256", "mailbox=3:64", "gpio=4:180", "rng=5:40", "dma=6:256"]
```

`profiles/pi4-release.d/devd.manifest`:

```toml
name = "devd"
exec = "/sbin/devd"
args = ["devd", "dtb", "launch"]
needs = []
provides = ["scheme:plat", "scheme:dev"]
readiness = "scheme"
ready_timeout_ms = 60_000
restart = "never"
max_restarts = 0
enable = true
```

`profiles/pi4-release.d/platd.manifest` must stay disabled (or be removed): devd launches platd,
so a second svcd service would register a duplicate `plat:` server.

`profiles/pi4-release.d/genet.manifest` keeps `needs = ["logd", "scheme:plat"]`; netd waits for
`scheme:nic` (REL4d). The devd readiness gate above is `scheme:plat`; the `nic:` sequencing is
REL4d work, not P8b.

The platd node's three `reg` windows are transferred as handles 3/4/5 in order, and the DMA is
handle 6. The parser accepts any distinct handles >= 3 and the minimum lengths; the table above
matches the P8b order.

## 5. Tests and acceptance

```sh
cargo nextest run -p raven-devd
cargo nextest run -p raven-platd
cargo xtask qtest --case pi4-devd --arch aarch64
cargo xtask qtest --case pi4-platd --arch x86_64
cargo check -p raven-devd --target aarch64-unknown-none-softfloat
make check-fast
```

The package is `raven-platd`; the binary is installed as `/sbin/platd`. The launcher tests cover
the single-BAR and multi-window plans, duplicate/out-of-range rejection and grant order. The
resource plan tests cover the four windows, P8 token passthrough, missing/short/duplicate/
reserved handles and unknown arguments. The `pi4-platd` qtest covers the three-window launch,
`plat:` scheme and client output. The board and the real window mapping remain UNVERIFIED; the
qtest uses the `fake` backend.
