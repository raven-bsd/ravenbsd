## Method

`scripts/repro-release.sh` builds each image twice into separate output files (`a.img`, `b.img`)
from the same clean commit and compares the size and SHA-256. It also copies the constituent build
artifacts (`kernel.elf`, `loader.efi`, `initfs.img`) after each build and compares them, so a
difference is attributed to a named input instead of being reported as a bare hash mismatch.

```
sh scripts/repro-release.sh
sh scripts/repro-release.sh --self-test
```

The script **requires a clean working tree** and pins `SOURCE_DATE_EPOCH` to the commit time.
Before trusting a build it checks that the kernel carries the current `git rev-parse --short
HEAD` id; a kernel cached from another commit or from a dirty tree fails the check instead of
producing a misleading pair. The image builder owns the same guard in `xtask/src/build.rs` and
`xtask/src/image.rs`: the x86_64 `release` and Pi 4 `pi4-release` profiles fail on a dirty tree,
on a `--kernel` override, and on a produced kernel without the clean whole HEAD id.

The self-test exercises only the comparison/diagnosis logic on synthetic files (identical,
same-size different-content, different-size, first differing byte, SHA-256 width, and the
clean/dirty/stale build-id classification). It does not build an image and cannot produce a
release verdict.

## The commit id is an input (observed)

The kernel banner embeds `RAVEN_BUILD_ID` = `<short>[-dirty] <commit-date>`
(`xtask/src/build.rs`), and `xtask` pins `SOURCE_DATE_EPOCH` from the commit. Therefore:

* two builds of the **same clean commit** are byte-identical (the table above records the pair);
* a dirty tree adds `-dirty` and changes the image hash, even when the product sources are
  unchanged (observed while an earlier ticket's files were uncommitted: the image carried
  `24f8cbff-dirty` and differed from the later clean `d64a6940` build);
* a different commit changes the id and therefore the image hash, by design.

A release artifact hash is only meaningful together with the commit it was built from. Build the
packet from a clean tag/commit, as `scripts/release.sh` already requires.

## What a future difference means

If a run reports a difference, the script prints the first differing image byte and compares the
three artifacts:

* **ELF `kernel.elf`/`loader.efi` differs** — inspect the GNU build-id (`readelf -n`) and the
  `.comment` toolchain string. Fix site: the profile/build flags in `xtask/src/image.rs` and
  `xtask/src/build.rs`.
* **`initfs.img` differs** — the RAVENFS1 header or per-entry timestamps/modes. Fix site:
  `xtask/src/initfs.rs` (fixed epoch/commit id instead of a wall clock).
* **All artifacts match but the image differs** — FAT directory timestamps, GPT disk/partition
  GUIDs or the generated `boot.toml`. Fix site: `xtask/src/image.rs` (fixed FAT mtimes and
  deterministic GUIDs).
* **Only a path/toolchain string differs** — check `CARGO_TARGET_DIR`/checkout-path embedding
  and the pinned `rustc --version`.

## Scope

The two builds share the checked-out tree and `target/` (compiler artifacts are reused); the
image assembly — initfs regeneration, FAT, GPT and boot.toml — runs on every invocation, which is
where the image-builder timestamp risks live. Compiler determinism from an empty cache and a
different checkout path is not isolated by the default run; that would be a separate, slower
mode.
