# RavenBSD 0.1.0 release notes

Status: **BLOCKED — both candidate images are built; the Pi 4 board chain is missing and 0.1.0 is not tagged.**
The x86_64 and Pi 4 release images below were built from the release profiles at `origin/master`
`4a4b9ebd` without an environment override. The QEMU release-login transcript passes
`tests/fixtures/release/check-transcript.sh`, the Pi 4 host-side image check passes and the REL8
clean-clone verifier passes its image pair. No Pi 4 board serial/GENET log exists, so every board
claim is **UNVERIFIED**; the owner must not tag 0.1.0 until the board chain and the full `make
check` pass.

Build commands (no environment override; REL7b made the release profile self-contained):

```sh
make image ARCH=x86_64 PROFILE=release

RAVEN_RPI_FIRMWARE=/path/to/rpi-firmware/boot \
    make image ARCH=aarch64 PLATFORM=pi4 PROFILE=pi4-release
```

`profiles/release.toml` sets `[initfs] release = true`; `cargo xtask image` resolves that switch and
builds the user programs with the release profile (REL7b). The current `pi4-release` profile does
not yet set the switch, so the Pi 4 candidate currently uses the profile-default user binaries;
REL3c finalizes the Pi 4 release profile. Both builds are candidates until the Pi 4 board chain
passes; no board result is claimed here.

## 3. Pi 4 image and board chain

The Pi 4 release image is built and its host side passes:

```sh
RAVEN_RPI_FIRMWARE=/path/to/rpi-firmware/boot \
    sh scripts/pi4-release.sh --check -i build/aarch64/ravenbsd-pi4.img
# pi4-manifest: PASSED
# pi4-release: kernel8.img banner marker ok
# pi4-release: release initfs paths ok (including /etc/pi4.dtb)
# pi4-release: image check PASS (board gates remain UNVERIFIED)
```

The **Pi 4 gate** is the board chain P8/P8b/P10/P12/REL3c:

* P8 — devd platform driver launch from the device tree;
* P8b — multi-window platform grants;
* P10 — the platform root grant for devd (merged);
* P12 — platd Pi 4 platform handles (mailbox, GPIO, RNG, DMA);
* REL3c — enable platd in the Pi 4 release profile and finalize the platform profile.

P8 and P10 are merged; P8b, P12 and REL3c remain in progress. There is **no Pi 4 board serial or
GENET log** yet, so the Pi 4 gate remains **UNVERIFIED**: no login, `ls /bin`, `ping` or GENET
link/DHCP claim is made for the board. `tests/fixtures/pi4-release/gate-markers.txt` and
`scripts/pi4-net-evidence.sh` define the required evidence, but a fixture is not a board result.

## 4. Independent clean-clone verification (REL8)

```sh
sh scripts/release-verify.sh /tmp/opencode/release-refresh
```

The verifier clones `origin/master` at `4a4b9ebd` into a fresh scratch directory, runs
`make setup --check` and `make release-gate`, builds the release image twice with the commit-time
`SOURCE_DATE_EPOCH`, and compares the two SHA-256 values. It never modifies the verifier tree and
never tags. An observed run:

```
release-verify: commit=4a4b9ebdb34d3abd1078745482956814576523fd time=1794836045
release-verify: image1 sha256=c6c216dc32af4e0326e0966e42d33f2914950bfdaf20b359ce5b2da8bbe2b9cc
release-verify: image2 sha256=c6c216dc32af4e0326e0966e42d33f2914950bfdaf20b359ce5b2da8bbe2b9cc
release-verify: PASS commit=4a4b9ebdb34d3abd1078745482956814576523fd
```

The REL8 pair is built after the gate, whose generated `Symbols.list` makes the clone
`4a4b9ebd-dirty`; it is a reproducibility check, not the clean candidate hash in section 1, and
the pair value is run-local (the REL5c report records the cross-run observation). REL8 verifies the
x86_64 QEMU image only; it is not a Pi 4 board result.

## 5. Evidence harness

default image paths are the `make image` outputs above.


## 6. Known limitations

* **Pi 4 board chain missing.** No board serial log, login/ping transcript or GENET evidence. Every
  Pi 4 board claim is UNVERIFIED. No `0.1.0` tag exists.
* **Pi 4 release profile not final.** `pi4-release` does not yet set the REL7b release switch, so
  its candidate uses the profile-default user binaries; REL3c finalizes the Pi 4 release profile.
* **rsh, not brush.** Brush is installed but experimental; its native spawn backend is pending P9a,
  so the 0.1.0 interactive session is rsh. No browser is shipped.
* **No signed artifact/SBOM.** `make sbom` is described by architecture/10 but has no target; the
  images are not signed.
* **Both release images are candidates.** They are reproducible from the release profiles but
  cannot be published as 0.1.0 until the Pi 4 board chain and full `make check` pass.

## 7. Default password warning

The release login is **`root` / `raven`**. That is a development default, not a production
credential. Change it before exposing the QEMU instance or a Pi 4 board to any network, and do not
reuse it on a real system. REL1b's release root shadow hash and the 0.1.0 gate remain byte-for-byte
compatible.

## 8. Final gate checklist (owner)

1. Complete the Pi 4 board chain (P8/P8b/P10/P12/REL3c), build the Pi 4 release image and capture
   the board serial and GENET ping logs.
2. Run `scripts/release-evidence.sh --pi4-log <board.log> --pi4-net-log <net.log>`; every Pi 4
   marker must pass. No board claim without the log.
3. Run `sh scripts/release-verify.sh /tmp/opencode/release-refresh` and the full `make check` on
   the final release commit.
4. Re-run `scripts/release.sh --build` on the final release commit to lock the published image
   hash, then `scripts/release-evidence.sh --record`; review `evidence.txt`.
5. Only then tag the commit and publish the images, image SHA-256 values, notes, evidence and
   provenance.
