## What 0.1.0 is

RavenBSD 0.1.0 is the first public source + QEMU release candidate: a Rust microkernel and
loader, the service set (init/initfsd/svcd/vfsd/consd/logd/netd/...), ravenlibc, the brush shell,
the base userland and the QEMU `release` profile. x86_64 is the primary QEMU target; aarch64
shares the kernel/userland sources and the Pi 4 release profile.

The release gate is deliberately conservative: a known reliability gap is a blocker, not a
waiver. The items below are green on the current evidence; the remaining NO-GO rows are listed
after them.

### Release-image login — BLOCKED (stale loader / K131)

The `c1e85d4c` release image failed on its first TCG4 boot with
`svcd: getty failed: bad ELF: SegmentOutsideUserRange`. S129 fixed the `raven-spawn` parse bound
(`0..USER_END`, with the post-bias user-range check), but S130's audit found the deeper cause:
the image's `ld-elf.so.1` had its first `PT_LOAD` at `vaddr=0`, while the loader contract is
`--image-base=0x1000`. A fresh `libc-link` produces the 0x1000 loader; `ensure_libc` only builds
when the file is missing, so a stale vaddr-0 artifact slipped into the release image. With that
stale loader the self-relocation fails because the loader reads its header at `AT_BASE + 0x1000`.
K131/Kevin fixes the build to rebuild/verify the loader and assert the 0x1000 contract in the
manifest; S130-r1 adapts the login test to the supported release shape and asserts the fresh
loader. The release image cannot be claimed green until K131 lands and the final TCG4 10/10 and
freeze-commit boot are rerun. The old `6d1b1bde` release-login PASS used the 0x1000 workspace
loader; it is not by itself freeze evidence.

### aarch64 concurrent TLB — BLOCKED

S103 rework 3 (`7372c442`) found a deterministic aarch64 SMP defect:
`smp-tlb-aarch64-concurrent` fails at iteration 0 with six
`aarch64-smp: tlb shootdown timeout` lines (`waiters=4`, `tlb_rounds=64`, `tlb_stale=0`). The
single-controller case is **50/50** green and `libc-threads` aarch64 passes; the concurrent
protocol is the blocker. The named cause is the address-space lock held across
`shootdown::flush_range()`: on aarch64 the SVC entry masks `PSTATE.DAIF`, so a peer spinning on
the mutex cannot take the TLB SGI. Owner: **S128/Stuart**. S103/S106 stay blocked; no timeout
raise, retry or test weakening. The preserved log is
`build/qtest/smp-aarch64/smp-tlb-aarch64-concurrent-aarch64-0.log`. This row is **BLOCKED /
NO-GO**.
