## What 0.1.0 is

RavenBSD 0.1.0 is the first public source + QEMU release candidate: a Rust microkernel and
loader, the service set (init/initfsd/svcd/vfsd/consd/logd/netd/...), ravenlibc, the brush shell,
the base userland and the QEMU `release` profile. x86_64 is the primary QEMU target; aarch64
shares the kernel/userland sources and the Pi 4 release profile.

The release gate is deliberately conservative: a known reliability gap is a blocker, not a
waiver. The items below are green on the current evidence; the remaining NO-GO rows are listed
after them.

### Release-image login — FIXED by S129 + K131 (final rerun pending)

The `c1e85d4c` release image failed on its first TCG4 boot with
`svcd: getty failed: bad ELF: SegmentOutsideUserRange`. S129 fixed the `raven-spawn` parse bound
(`0..USER_END`, with the post-bias user-range check). S130's audit then found the deeper cause:
the image's `ld-elf.so.1` had its first `PT_LOAD` at `vaddr=0`, while the loader contract is
`--image-base=0x1000`; `ensure_libc` reused a stale workspace artifact. With that stale loader,
self-relocation failed at `AT_BASE + 0x1000`.

K131 fixed the build: a release build now purges and relinks the dynamic loader from current
sources, writes a loader manifest, and verifies the packed initfs bytes. The x86_64 image at
`fd394ff3` carries the fresh 0x1000 loader (`sha256=7bc53cec…`) and is A/B byte-identical. S130-r1
is adapting `release-login` to assert the supported 0x1000 shape and the fresh loader. The final
TCG4 10/10 and freeze-commit boot are still required before login evidence is freeze-grade.

### aarch64 concurrent TLB — FIXED by S128

S103 rework 3 (`7372c442`) found a deterministic aarch64 SMP defect:
`smp-tlb-aarch64-concurrent` failed at iteration 0 with six
`aarch64-smp: tlb shootdown timeout` lines (`waiters=4`, `tlb_rounds=64`, `tlb_stale=0`). The
cause was the address-space lock held across `shootdown::flush_range()`: on aarch64 the SVC entry
masks `PSTATE.DAIF`, so a peer spinning on the mutex cannot take the TLB SGI. S128 moved the
shootdown/frame recycle outside the lock and added the per-CPU lock probe.

The clean S128 matrix at `a8f960ac` is **concurrent 50/50, single-controller 50/50, user 50/50,
soak 5/5, x86/libc 5/5, 0 timeout lines**. The earlier iter-37 failure under host load is
preserved. S140 reran the kernel gate at the current tree: **27/27 at `f803502a`** (x86_64 22/22,
aarch64 5/5, 541.92 s). This TLB fix is separate from the x86 `smp-libc-concurrency` failure,
which is a libc thread bug.

### libc thread 1-CPU crash — BLOCKED

`smp-libc-concurrency` fails at **one CPU**, so it is not an SMP/TLB failure:

process: child exited (-11)

### Interactive shell — BLOCKED

The `boot-qemu` demo exposed three interactive defects, separate from the network and the release
gates:

- `process: child exited (0)` after every command (S97/Stuart: quiet normal child-exit logging;
  keep the PID 1 `init exited` marker).
- `ls` takes 2-3 s every time in the demo-login image (K133/Mel: spawn/loader vs uutils
  stat/readdir vs vfsd/ramfs timeout).
- `du` aborts with `fatal runtime error: current thread handle already set during thread spawn`
  (K134/Tim). The first failure is the uutils link script: the first `PT_LOAD` does not map the
  ELF/program headers, so `PT_TLS` discovery fails and the first thread spawn aborts; K136/Kevin
  fixes the link layout, then K134 retests the thread start/exit/join path.
- getty takes 1.3-2.5 s from `root`+ENTER to `Password:` while the typed line echoes immediately
  (K135/Phil; the same console-write cluster as K133, not the password check). K135/K139 proved the
  delay is the **dynamic loader**, not the password check; the packet row is `cold-start`
  (**PENDING K139**).

These block the interactive demo/tag until fixed and revalidated. The generated packet now carries
the `cold-start` row (`PENDING K139`); the gate board carries S97/K133/K134/K135/K139.
`ldblk` is not a command; the disk
tool is `lsblk`, and the fast demo-login image does not stage the full release disk tools. The fast
