## Owner board checklist

Record every item under `tests/evidence/pi4/<new-image-sha256>/`; keep logs small and paste their
SHA-256 into the release packet.

### 1. Rebuild, flash, boot (owner)

```sh
RAVEN_RPI_FIRMWARE=/path/to/ravenbsd-resources/rpi-firmware/boot \
  SOURCE_DATE_EPOCH=1700000000 \
  cargo xtask image --arch aarch64 --platform pi4 --profile pi4-release
RAVEN_RPI_FIRMWARE=/path/to/ravenbsd-resources/rpi-firmware/boot \
  SOURCE_DATE_EPOCH=1700000000 \
  cargo xtask image --arch aarch64 --platform pi4 --profile pi4-rootfs

sh scripts/pi4-release.sh --check
sh scripts/pi4-ui-evidence.sh --check

# never guess the card device
sudo sh scripts/pi4-install.sh --flash /dev/sdX --yes \
  -i build/aarch64/ravenbsd-pi4-sd.img
```

Insert the card, connect HDMI monitor, USB keyboard and a 3.3 V USB-UART adapter (115200 8N1,
**no VCC**), then power on.

### 2. Serial capture (produces `serial.log`)

```sh
sh scripts/pi4-ui-evidence.sh --capture -d /dev/ttyUSB0 \
  -l tests/evidence/pi4/<sha>/ui1-serial.log
```

Capture must include the header (`# image sha256`, `# commit`, `# device`), the Pi 4 board marker
(`bcm2711`/`raspi4b`), login/password/`raven#`, `/bin/uname` showing `RavenBSD`/`aarch64`, dynamic
`NEEDED libc.so.1`, GENET link up + DHCP, a ping reply and `init exited (0)`. Validate:

```sh
sh scripts/board-pi4-check.sh --log tests/evidence/pi4/<sha>/ui1-serial.log
```

A QEMU/virt/synthetic log is refused; do not present one as board evidence.

### 3. HDMI/USB login (produces `hdmi-usb.jpg` and `login.md`)

On the monitor: kernel banner, login policy, one wrong password, then `root`/`raven`; run
`/bin/uname -a`, `/bin/ls /bin`, `ping <gateway>`, then `exit 0`. Record the monitor model/native
resolution, keyboard model, cable/adapter and image SHA in `login.md`; photograph the monitor at
the login or shell prompt as `hdmi-usb.jpg`.

### 4. E-Ink demo (produces `eink-panel.jpg` and `docs/eink-demo-evidence.md`)

Requirements:

- Panel SKU/revision: Waveshare 7.5-inch V2-class UC8179, 800x480, full refresh only.
- Owner-approved plain-HTTP fetch URL, exact URL and SHA-256 of the fetched page.
- NTP-corrected time in the einkd log (`next_at`) and the configured refresh interval.
- One successful fetch → render → full refresh; a second refresh/change if the content updates
  (or a recorded reason it does not).
- Photo of the physical panel showing the fetched page, with the board visible; no composite,
  mock render or borrowed image.
- Keep the `einkd` serial lines (`fetch`, `render`, `refresh`, `next_at`) in the same `serial.log`
  or a second log with its SHA-256.

Then write `docs/eink-demo-evidence.md` with the photo paths, serial log, image SHA-256, panel
SKU, fetch URL/hash, NTP time, refresh interval and a short website-ready description. E5 owns
that document; this page only defines its required inputs.
