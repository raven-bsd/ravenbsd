# Fuzzing the syscall and parser boundaries (S20)

The kernel syscall dispatcher, the user-copy bounds checks, the handle table and the ELF loader are
security boundaries that had only happy-path tests. This document describes the host-side fuzz
harness: what it targets, how a finding is reproduced, and what it deliberately does **not**
cover. Evidence tags as in `architecture/00`: OBSERVED, PROPOSED, UNVERIFIED.

## 1. Shape

```
crates/raven-fuzz-model   the targets: byte slices in, invariants checked (host, stable Rust)
tools/fuzz                the `raven-fuzz` driver: seeded mutation sweeps + corpus replay
tests/fuzz/corpus         the committed corpus, one directory per target, hex text
tests/fuzz/replay         `raven-fuzz-replay`: replays corpus + seed + sweep under `cargo test`
tests/fixtures/s20-fuzz   crash reproducers (empty; the convention lives in its README)
```

The targets drive the **real** host-testable code the kernel uses: `raven_abi` syscall numbering
and errno mapping, `raven_usercopy` range validation, `raven_handles` handle table, `raven_elf`
parsing and load planning, and `raven_ipc` packet decoding. The kernel-only halves (the syscall
entry stubs, the fault-safe copy in assembly, page-table installation) are out of scope for a
host harness and are covered by the qtests instead.

## 2. Targets

| Target | Boundary | Invariants checked |
|---|---|---|
| `syscall` | `Syscall::from_usize`, `Errno::from_ret` | an accepted number maps back to itself; the 0..=0x40 window never panics; a negative return in `-4095..0` round-trips through `to_ret`; values outside that window never become errnos |
| `usercopy` | `validate_range`, `UserSlice::new_in`, `UserPtr` | no panic; an accepted range lies inside the checked range; a wrapping range is rejected; both validators agree |
| `handles` | `HandleTable::{insert,get,dup,close}` | `len` tracks live handles; `get` never returns fewer rights than asked; `dup` never widens rights; a closed handle stops resolving; a double close is an error |
| `elf` | `Elf::parse`, `plan_load` | no panic; a plan is page-aligned, inside the user range, sorted, non-overlapping, and uses only `R|W|X` bits |
| `ipc` | `protocol::{decode,encode,validate}` | no panic; a decoded packet re-encodes and decodes to the same opcode, id and path; validation is stable across the round trip |

Each target is `fn(&[u8])`: the same function is called by the tool, by the replay tests and by a
future Miri or libFuzzer driver without changes.

## 3. Corpus and replay

* One directory per target, `tests/fuzz/corpus/<target>/*.hex`.
* A corpus file is hex digit pairs; whitespace and `#` comments are ignored. Files are small and
  textual so a diff is readable and the provenance rule is trivial: they are hand-written, except
  `ipc/open-request.hex`, which is documented as generated by
  `cargo run -p raven-fuzz -- --print-seed ipc`.
* `cargo test -p raven-fuzz-replay` runs every committed file on every target, plus the built-in
  seed and a 1000-iteration deterministic sweep - on stable Rust, with no fuzzer runtime.
* The built-in seed of each target is constructed in code (`raven_fuzz_model::seed`), so a target
  always has a valid starting point even if the corpus is empty.

## 4. Running

```
cargo test -p raven-fuzz-model                     # target unit tests
cargo test -p raven-fuzz-replay                    # committed corpus replay
cargo run -p raven-fuzz -- --all --corpus tests/fuzz/corpus --iterations 20000 --seconds 5
```

The driver prints, per target, the number of inputs and the elapsed time, and always prints the
PRNG seed first: a crash is reproduced with the same `--seed` and target.

### The soak (owner-run)

One hour per target is the goal and needs an idle machine:

```
for target in syscall usercopy handles elf ipc; do
  cargo run --release -p raven-fuzz -- --target "$target" \
    --corpus tests/fuzz/corpus --seconds 3600 --seed 1
done
```

Use `--release`: the debug build is roughly an order of magnitude slower per input.

## 5. Findings

An invariant violation is a finding. The policy is:

1. Reproduce it with the printed seed (`--seed <n> --iterations <k>`), minimise the input and
   commit it as `tests/fixtures/s20-fuzz/<target>-<n>.hex`.
2. Add it to the replay (the corpus directories are read automatically if the file is placed under
   `tests/fuzz/corpus/<target>/`) and assert the fixed behaviour.
3. If the fix is outside S20's Owns (kernel or an owned crate), write the follow-up into the
   report; do not edit the kernel here.

## 6. Limits (stated, not hidden)

* The targets run the parsing and validation code, not the kernel's entry stubs or page-table
  installation; a bug that only exists in the assembly path needs a qtest.
* The handle-table target drives `raven_handles` directly, so it cannot see process-global handle
  policy (rights inheritance at spawn, transfer to another process).
* Mutations are single-input; there is no coverage feedback (no libFuzzer instrumentation in the
  stable build). The corpus and the five seeds compensate, but a coverage-guided nightly run is a
  possible follow-up (`tools/fuzz` is the place for it; no shipped crate may use nightly).
