# Filesystem parser fuzzing

Status: B37 harness for the UFS parser.  GPT and FAT parser targets are not
implemented because this tree contains only their image **builders**
(`xtask/src/gpt.rs`, `xtask/src/fat.rs`); there is no product GPT or FAT
parser to fuzz.  That finding needs a follow-up ticket when such a parser
lands.

## Targets

| Target | Overlay on the B63 golden image | Parser path |
|---|---|---|
| `ufs_superblock` | primary superblock, 1,376 bytes at 8192 | `Ufs::mount` geometry and superblock validation |
| `ufs_cg` | cylinder-group 0 header (`cgsize` bytes) | mount and lazy group access |
| `ufs_inode` | root inode (`bsize/inopb` bytes) | `getattr`, `lookup`, `readdir` |
| `ufs_directory` | root directory block (`fsize` bytes) | `readdir`, `lookup` |
| `ufs_indirect` | `blocks600.bin`'s first indirect block | `read` through the single-indirect path |

Every target starts from `tests/ufs-vectors/golden/ufs2-b4096.img.gz` (the B63
NetBSD `makefs` image) and overlays the fuzz input on one region.  Replay
mounts it read-only and exercises `getattr(2)`, `lookup(2, "empty")`,
`lookup(2, "blocks600.bin")`, bounded `readdir(2)`, `read(3)` and, for the
indirect target, a read at logical block 20 of `blocks600.bin`.

## Stable replay

`raven-fs-fuzz-replay` is the stable-Rust replay harness.  It catches panics,
counts every out-of-range `BlockIo` read and returns an error for either one.
The corpus test reads every committed file under
`tests/fs-fuzz/corpus/<target>/` and requires at least eight seeds per target.

```
cargo test -p raven-fs-fuzz-replay
cargo test -p ufs-core
```

The corpus files are raw bytes for one target's overlay region, not whole
16 MiB images; `seed-00` is the pristine region and the other seeds are
deterministic byte mutations.  They are generated by:

```
cargo run -p raven-fs-fuzz -- seed
```

Binary corpus files are exempt from the SPDX header rule through
`.provenance-ignore` (`tests/fs-fuzz/corpus/`); their origin is the committed
B63 golden image above.

## Nightly fuzz tooling

The cargo-fuzz project lives in `tests/fs-fuzz/fuzz/`, has its own workspace
and is not built by `make check`.  It needs a nightly toolchain and
`cargo-fuzz`; only the tooling uses nightly, the replay library and the
shipped parsers stay on stable Rust.

```
rustup run nightly cargo fuzz run ufs_superblock tests/fs-fuzz/corpus/ufs_superblock
rustup run nightly cargo fuzz run ufs_cg tests/fs-fuzz/corpus/ufs_cg
rustup run nightly cargo fuzz run ufs_inode tests/fs-fuzz/corpus/ufs_inode
rustup run nightly cargo fuzz run ufs_directory tests/fs-fuzz/corpus/ufs_directory
rustup run nightly cargo fuzz run ufs_indirect tests/fs-fuzz/corpus/ufs_indirect
```

## Stable smoke runner

A deterministic mutational smoke run is available without nightly:

```
cargo run -p raven-fs-fuzz -- run --seconds 60 --seed 1
```

The tool prints the execution count per target.  The B37 report records the
actual smoke duration; no one-hour soak is claimed unless the owner ran it.

## Findings

- A panic, hang or out-of-range read is a parser defect.  The replay harness
  saves the failing input as a corpus file, replays it in
  `cargo test -p raven-fs-fuzz-replay` and the report names the seed.
- A defect outside `tests/fs-fuzz/**`, `tools/fs-fuzz/**` or the docs is a
  report plus a follow-up ticket; B37 does not edit parser behaviour.
- GPT/FAT: no parser exists in this tree, so no target can be honest.  When a
  parser is added, add its target to `TARGETS`, `region()` and the fuzz crate.
