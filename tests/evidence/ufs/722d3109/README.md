## Expectation changes (K234 + K374)

The six `qemu-ufs` cases (`ufs-root`, `ufs-root-persist`, `ufs-update`,
`ufs-update-persist`, `ufs-full`, `ufs-statfs`) now assert the current product
behaviour instead of the pre-K234/K374 one:

* **Styled boot screen (K374):** `^R A V E N   B S D$`, the 80-dash rule and
  `^Welcome to RavenBSD 0\.1 x86_64$`, before `login:`.
* **Getty restart (K234):** after `exit`, the case waits for `login:` to return,
  logs in a second time and re-proves its marker (`/persist-marker`,
  `/etc/ufs-update.txt`, the statfs fill file, or a one-disk echo). It then
  **forbids** `^init exited` and ends at a bounded 120-180 s timeout. The old
  `init exited (0)` expectation is gone because init no longer exits on this
  profile.
* `ufs-logout` keeps its timeout and two-login flow; only the old single-line
  banner expectation was replaced by the three screen lines.

Each case's product assertions (partition table, `ufs: on /`, markers, update
contents, network) are unchanged.

## `disk-tools` classification: real, not load

`disk-tools` fails on every current tree tested (`978899da`, `b04e71ad`,
`722d3109`) with the same serial:

```text
devd: driver virtio-blk irq line=11
virtio-blk: registered disk
devd: driver virtio-net msix unavailable: bad handle or file descriptor; using legacy irq
devd: driver virtio-net launch failed: irq: resource busy
svcd: devd failed: exited before it became ready
blockd: waiting for disk:0: no such file or directory
svcd: blockd failed: readiness timeout
```

Both virtio functions expose legacy PCI IRQ 11 (PIIX4 shared PIRQ); MSI-X setup
returns EBADF for both, so both fall back to the exclusive legacy GSI. The first
claim succeeds, the second returns `EBUSY`, and `devd` exits before serving the
scheme. This is a product defect in the MSI-X fallback / shared-INTx path
(`userland/servers/devd`, `kernel/src/driver/irq.rs`), not a load artefact and
not a UFS error. It is outside K413's Owns, so it is classified here and left for
its owner; the case was not weakened or skipped.

## Transients recorded (not used to excuse a failure)

* `ufs-disk-ufs1` r1: `mount ufs: /mnt` produced no prompt for 30 s; the UFS1
  image checked `clean` on the host. The r2 pass is 80 s. Kept as
  `serial/ufs-disk-ufs1-r1-transient.log`.
* `ufs-update` r1: the kernel reported `smp: cpu 1 did not start` /
  `smp: 1 cpus online` and QEMU exited before login (the S159-class AP
  bring-up failure). The r2 boot passed 189 s. Kept as
  `serial/ufs-update-r1-transient.log`.
* `ufs-full` r1 hit the 480 s outer cap during the pre rebuild; the leftover
  QEMU held the demo qcow2 write lock and blocked two image builds until it was
  killed by PID. The r2 with a 600 s cap passed in 180 s.
* `ufs-root-persist` was first run against a stale case ESP (no styled screen),
  then against a root disk regenerated by an image build (marker wiped). The
  final pair runs `ufs-root` and then `ufs-root-persist` with `--no-build` on the
  same disk, which is the case's documented order.
